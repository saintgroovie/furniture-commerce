# Архитектурные ограничения проекта

Этот документ фиксирует архитектурные ограничения системы.  
Перед реализацией любой новой функции необходимо проверить, что изменения не нарушают эти ограничения.

---

# 1. Общая архитектура

Проект использует простую архитектуру:

Medusa backend  
Next.js storefront  
PostgreSQL

Один backend-сервис.

Запрещено:

- вводить микросервисы
- добавлять BFF
- добавлять дополнительные backend-приложения
- создавать отдельные API gateway

---

# 2. Backend

Backend построен на Medusa.

Разрешено:

- кастомные модули в src/modules
- links между сущностями
- middleware
- кастомные REST endpoints

Запрещено:

- форкать Medusa core
- переписывать стандартные workflows
- дублировать core-логику Medusa

---

# 3. Storefront

Storefront — это Next.js приложение.

Storefront должен:

- обращаться к backend только через REST API
- не содержать бизнес-логики

Вся бизнес-логика должна находиться в backend.

---

# 4. Сущности данных

Основные сущности системы:

Product  
ProductClassification  
RoomSet  
RoomSetItem  
Lead  
BespokeRequest  
PaymentLink

Новые бизнес-сущности можно добавлять только если они соответствуют MASTER_PRD.

---

# 5. Типы товаров

Тип товара хранится в отдельной сущности ProductClassification (таблица `product_classification`, поле `product_type`).

Типы:

STANDARD  
CONFIGURABLE  
BESPOKE

Правила:

STANDARD — только корзина  
CONFIGURABLE — корзина + заявка  
BESPOKE — только заявка

BESPOKE товары никогда не должны попадать в корзину.

---

# 6. Room Sets

Room Sets — отдельная сущность.

Запрещено:

- моделировать Room Sets как категории
- моделировать Room Sets как collections

Связь:

RoomSet  
→ RoomSetItem  
→ Product

---

# 7. Leads и заявки

Lead — контакт клиента.

BespokeRequest — конкретный запрос на расчёт.

Связь:

Lead 1 → N BespokeRequest

---

# 8. Payment

PaymentLink — отдельная бизнес-сущность.

Для MVP используются только:

lead  
order

Оплата происходит через внешнюю ссылку.

---

# 9. Ограничение сложности

Перед реализацией функции необходимо проверить:

- не добавляет ли она новый архитектурный слой
- не дублирует ли она существующую логику
- не выходит ли она за границы MVP

Если добавляется новая абстракция — она должна быть обоснована.

---

# Как использовать guardrail

Перед реализацией любой новой функции необходимо:

1. Проверить соответствие архитектуре из `architecture/architecture-guardrails.md` (от корня `docs/`)
2. Проверить правила разработки из `guidelines/development-rules.md`
3. Проверить требования из `project/MASTER_PRD.md`

Если реализация противоречит этим документам — нужно изменить реализацию.
