# Repo cleanup plan — без разрушения истории

**Статус:** план и рекомендации; **без** автоматического удаления файлов, **без** `git filter-repo` / BFG в этом документе как выполненных действий, **без** force-push.  
**Связанный отчёт:** [`repo-weight-audit.md`](repo-weight-audit.md)  
**Контекст ветки:** `storefront/phase1-foundation-and-polish`, коммит `f22b53e`.

---

## 1. Цели и ограничения

**Цели**

- Отделить **исходный код и контрактные JSON** от **сырья, бинарников и runtime-копий**.
- Сохранить **воспроизводимость** seed и asset pipeline при явной процедуре onboarding.
- Не ломать модель: **один Medusa backend**, **тонкий storefront** ([`architecture-guardrails.md`](../architecture/architecture-guardrails.md)).

**Ограничения**

- Не переписывать историю в рамках «слоя A».  
- Не удалять из git потенциальный SoT, пока нет **замены** (внешний bucket, LFS, или задокументированный импорт).

## 2. Решения по спорным зонам (шаблон: решение / почему / риски / влияние)

### 2.1. `data/raw/` (~652 MiB)

| Поле | Содержание |
|------|------------|
| **Решение** | **Убрать из отслеживания в следующих коммитах** (`.gitignore` + `git rm --cached`) и хранить **во внешнем артефактном хранилище** или, как компромисс, **Git LFS** только для PDF + ограниченного набора. |
| **Почему** | Это **сырьё** экстракции и скрейпа; не код. Увеличивает clone и смешивает жизненный цикл данных с жизненным циклом приложения. |
| **Риски** | Новый клон без шага «скачать raw» **не** воспроизведёт полный пайплайн с нуля. |
| **Влияние** | **Reproducibility:** нужен **manifest** (checksums, версия набора) в `docs/` или JSON в `data/normalized/`. **Onboarding:** +1 шаг в README. **QA:** фиксировать версию набора raw для прогона. |

### 2.2. `data/processed/storefront-assets/` (~47 MiB)

| Поле | Содержание |
|------|------------|
| **Решение** | **Убрать из git** (ignore + stop-tracking), считать **сборочным выходом** скриптов препроцессинга. |
| **Почему** | Производное от raw; дублирует назначение materialized путей под backend. |
| **Риски** | Дольше первый прогон пайплайна локально. |
| **Влияние** | **Asset pipeline:** скрипты уже знают выходные пути — достаточно запуска по порядку. **Seed:** не читает эту папку напрямую, если финальные URL указывают на `/static` или `/uploads`. |

### 2.3. `apps/backend/uploads/products/` и `apps/backend/static/products/`

| Поле | Содержание |
|------|------------|
| **Решение** | **Убрать обе из git** (рекомендуемый минимум — **хотя бы одну**; сейчас деревья **идентичны** — см. аудит). Оставить в репо при необходимости пустые каталоги через `.gitkeep` **не** для тысяч файлов. |
| **Почему** | Это **runtime-артефакты** Medusa; восстанавливаются `upload-assets-to-local-storage.py` (static) и `deploy-greenwich-assets.py` (uploads). Две копии вводят в заблуждение (см. также QA по `/uploads` vs `/static` в URL). |
| **Риски** | Пустой clone без прогона скриптов — пустые картинки до выполнения шага. |
| **Влияние** | **Seed flow:** требует файлы на диске — документировать единый шаг «materialize assets». **Onboarding:** явная команда после clone. |

### 2.4. `data/processed/asset-manifests/local-upload-*.json`

| Поле | Содержание |
|------|------------|
| **Решение** | **Игнорировать** или коммитить только **при релизе QA** (процессом). По умолчанию — **gitignore**. |
| **Почему** | Лог конкретного прогона; пересоздаётся скриптом. |
| **Риски** | Меньше «следов» в git для пост-аудита — компенсировать выгрузкой в CI или приложением к тикету. |
| **Влияние** | **QA:** при необходимости хранить снимки вне репо. |

### 2.5. `data/normalized/*.json` (кроме явного мусора)

| Поле | Содержание |
|------|------------|
| **Решение** | **Оставить в git** (возможно сократить набор «ревью» файлов позже). |
| **Почему** | Контракт для `seed-real-data.ts`, Greenwich seed, манифестов и документации. |
| **Риски** | Минимальные (~4 MiB суммарно). |
| **Влияние** | **Прямой SoT для воспроизводимого seed** в текущей архитектуре: `seed-collections.json`, `seed-categories.json`, цепочка `seed-products.fixed2.json` → `seed-products.fixed.json` → `seed-products.json`, `seed-assets.json`, плюс маппинг (`entity-mapping.json`, `product-asset-binding.json`, execution manifest для upload). |

### 2.6. Скрипты `scripts/*.py` и `*.ts` в `apps/backend/src/scripts/`

| Поле | Содержание |
|------|------------|
| **Решение** | **Оставить** — часть воспроизводимости. |
| **Почему** | Код и контракт выполнения. |
| **Риски** | — |
| **Влияние** | Позволяет не хранить тяжёлые выходы, если документирован порядок запуска. |

## 3. Вопросы из задания (кратко)

### 3.1. Нужны ли raw-входы постоянно **в этом** git-репозитории?

**Не обязательно**, если есть **альтернатива**: версионируемый архив + checksum в репозитории, или корпоративное хранилище. Для **полной** пересборки с нуля без внешних сервисов — нужны **где-то**; не обязательно в том же repo, что приложение.

### 3.2. Какие normalized файлы — SoT для воспроизводимого seed?

**Минимум для real-data draft seed (код):**

- `seed-collections.json`, `seed-categories.json`
- Один из: `seed-products.fixed2.json` / `seed-products.fixed.json` / `seed-products.json`
- `seed-assets.json` (URL и привязки к файлам, согласованные с materialization)

**Для целостности пайплайна (рекомендуется держать под VCS):**

- `entity-mapping.json` (+ excluded/summary по политике)
- `product-asset-binding.json` (+ summary/schema)
- `asset-upload-execution-manifest.json` (или актуальное имя манифеста, который читает upload-скрипт)

**Greenwich:** `greenwich-ingestion.json` — читается seed/refresh скриптами.

### 3.3. Что можно пересоздать, а что нет?

| Артефакт | Пересоздаваемость |
|----------|-------------------|
| `data/raw/*` | Только если сохранены **источники** (PDF, доступ к legacy сайту, дисковые копии) и скрипты; иначе **нельзя** без внешнего архива. |
| `data/processed/storefront-assets` | **Да**, из raw + скрипты. |
| `apps/backend/static/products`, `uploads/products` | **Да**, из processed + upload/deploy скрипты (при наличии исходников или зеркала). |
| `data/normalized/seed-*.json` | **Частично:** если есть генератор из workbook/mapping; иначе **нельзя** без восстановления входов. Текущий repo предполагает **JSON как зафиксированный слой**. |

### 3.4. Смешаны ли исходники и one-off execution artifacts?

**Да:** в одном коммите оказались и код, и полный raw, и двойная materialization, и логи upload. Это и есть триггер cleanup.

## 4. План по слоям

### Layer A — non-destructive (следующие коммиты, история сохранена)

1. **Зафиксировать политику** в `docs/project/`: аудит, этот план и **runbook** — [`repo-onboarding-and-assets-runbook.md`](repo-onboarding-and-assets-runbook.md) (onboarding, материализация ассетов, контракт `data/normalized`).  
2. **Расширить `.gitignore`** по согласованным паттернам из [`repo-weight-audit.md`](repo-weight-audit.md) §5 + `.gitkeep` под игнорируемыми корнями.  
3. **`git rm --cached`** для путей, которые больше не должны отслеживаться (файлы остаются локально до следующего clean, если нужно).  
4. **Два сценария materialization** задокументированы в runbook: `upload-assets-to-local-storage.py` → `apps/backend/static/`; `deploy-greenwich-assets.py` → `apps/backend/uploads/products/greenwich` (без рефакторинга кода).  
5. **Опционально:** `.gitattributes` с `export-ignore` для релизных tarball исходников (не уменьшает историю, удобство упаковки) — **не вводилось** на шаге Layer A.

**Риски Layer A:** мало. **Обратная совместимость:** старые коммиты по-прежнему содержат тяжёлые blob — **clone остаётся тяжёлым**, пока не Layer C.

### Layer B — medium-risk (по согласованию команды)

1. **Git LFS** для подмножества PDF/крупных PNG **или** один **LFS**-пакет «catalog-sources».  
2. **Реструктуризация `data/`:** например `data/normalized` остаётся; `data/raw` → документ «скачать набор vN».  
3. **CI job:** после merge проверка «манифест нормализованных файлов + dry-run скрипта» без коммита бинарников.

**Риски:** LFS-квоты, сложность для внешних контрибьюторов.

### Layer C — high-risk history cleanup (только рекомендация)

**Когда оправдано:** договорённость команды, мало активных веток от старых коммитов, готовность **пересоздать** форки и обновить default branch после **filter-repo** или BFG.

**Что чистить:** пути `data/raw/**`, дубли `apps/backend/static/products/**`, `apps/backend/uploads/products/**`, `data/processed/storefront-assets/**` — из **всей** истории.

**Риски:**

- Ломаются SHA всех последующих коммитов; все клоны должны **re-clone** или hard-reset.  
- Открытые PR и ветки требуют rebase/cherry-pick.  
- Подмодули и подписи коммитов (если используются) усложняются.

**Не выполнять**, пока Layer A не принят и не измерен эффект на процесс (часто Layer A достаточно для **новых** коммитов, а тяжёлая история остаётся как «налог прошлого»).

## 5. Что сделать прямо сейчас vs отложить

### Сейчас (безопасно)

- Принять текстовую **политику** (этот план + аудит).  
- Решить: **одна** целевая копия бинарников на машине разработчика (`static` **или** `uploads` + единый ASSET_BASE_URL в доках).  
- Подготовить **чеклист onboarding** (5–7 шагов: clone, зависимости, optional download raw, run preprocess, run upload).  

### Скоро (Layer A в коде)

- `.gitignore` + `git rm --cached` для согласованных деревьев.  
- Коммит только с изменениями правил и документации + удалением tracking (без `filter-repo`).

### Отложить

- **History rewrite** (Layer C), пока нет сильной боли по CI minutes / fork size.  
- Массовый **LFS**, пока не выбран хостинг и квоты.

## 7. Финальный вердикт

| Критерий | Оценка |
|----------|--------|
| **Временно продолжать работу как есть** | **OK** — функционально репозиторий целостен. |
| **Долгосрочно оставлять как есть** | **Не OK** — размер, дубли runtime, смешение слоёв данных. |

Следующий логичный шаг после утверждения плана: **Layer A** одним коммитом (ignore + stop-tracking + короткая инструкция в docs), без переписывания истории.
