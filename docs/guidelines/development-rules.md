# Правила разработки

Эти правила обязательны при реализации любых новых функций.

## 1. Документация — источник истины

При разработке необходимо следовать документам в `/docs` (пути от корня репозитория):

- `docs/project/MASTER_PRD.md`
- `docs/architecture/architecture.md`
- `docs/architecture/data-model.md`
- `docs/guidelines/product-rules.md`
- `docs/architecture/admin-flows.md`
- `docs/project/mvp-scope.md`

Если код противоречит этим документам — нужно исправлять код, а не менять архитектуру.

---

# Архитектурные правила

## 2. Не усложнять архитектуру

Запрещено:

- вводить новые слои архитектуры без явной необходимости
- добавлять абстрактные сервисы, фабрики, generic-framework код
- создавать новые приложения или сервисы

Проект должен оставаться:

Medusa backend  
+  
Next.js storefront  
+  
PostgreSQL

Без микросервисов и BFF.

---

## 3. Бизнес-логика только в модулях

Бизнес-логика должна находиться:

src/modules/*

Route handlers (`src/api/...`) должны:

- принимать запрос
- вызывать сервис
- возвращать ответ

Route handlers **не должны содержать бизнес-логику**.

Временное и узкое исключение только для Phase 1: GET /store/products может выполнять оркестрацию query в route (фильтры по category_id, product_type). Это исключение не распространяется на другие route handlers и должно быть снято при выносе логики в сервис.

---

## 4. Не менять ядро Medusa

Запрещено:

- форкать Medusa core
- переписывать стандартные workflows
- дублировать core-логику

Расширение должно происходить через:

- кастомные модули
- links
- middleware

---

# Правила модели данных

## 5. Типы товаров

Система использует три типа товаров:

STANDARD  
CONFIGURABLE  
BESPOKE

Правила:

STANDARD — можно в корзину  
CONFIGURABLE — можно в корзину и можно отправить запрос  
BESPOKE — нельзя в корзину, только запрос

**BESPOKE товары никогда не должны попадать в корзину.**

---

## 6. ProductClassification

Тип товара хранится в отдельной модели:

ProductClassification

Таблица: `product_classification`. Поле: `product_type` (enum: STANDARD | CONFIGURABLE | BESPOKE).

Связь:

Product 1 → 1 ProductClassification

Это бизнес-правило проекта.

---

## 7. Room Sets

Room Set — отдельная бизнес-сущность.

Запрещено моделировать Room Sets как:

- collections
- categories

Связь:

RoomSet  
→ RoomSetItem  
→ Product

---

## 8. Lead и BespokeRequest

Разделение сущностей обязательно.

Lead — контакт клиента  
BespokeRequest — конкретный запрос на расчёт

Связь:

Lead 1 → N BespokeRequest

---

## 9. PaymentLink

PaymentLink — отдельная бизнес-сущность.

Назначение:

ручная оплата через внешнюю ссылку.

Для MVP поддерживаются только сущности:

lead  
order

---

# Правила разработки

## 10. Не генерировать комбинации вариантов

Запрещено автоматически генерировать комбинации вариантов товаров.

Все варианты должны создаваться явно.

---

## 11. Предпочитать простой код

Всегда выбирать:

- простой код
- явную логику
- минимальное количество абстракций

Запрещено писать «умный» или слишком обобщённый код.

---

## 12. Не выходить за границы MVP

Если функция отсутствует в:

mvp-scope.md

её нельзя добавлять.

---

# Правила публичного naming

## 13. Публичные labels storefront

Все user-facing labels (навигация, headings, CTA, filter tabs, badges) должны соответствовать:

naming-system.md

При добавлении нового label — сначала добавить его в `naming-system.md`, затем использовать в коде.

Legacy labels из таблицы в `naming-system.md` не использовать как primary public labels.

---

# Поведение при неясности

Если требование неясно:

1. Следовать документации в `/docs`
2. Выбрать самое простое решение
3. Не расширять архитектуру
