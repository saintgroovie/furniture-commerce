The owner explicitly authorized companies, employee assignment and team access from other computers on 2026-10-21. The approved application entry point is `https://woodright.ru/os`. This supersedes the previous local-only workspace boundary for this authenticated BFF only. Raw Medusa Admin stays private; its CORS, port exposure and routes are unchanged. 1C and MANGO stay off.

Build clean, qualified main images through the existing pair image workflow and `build-workspace-image.yml`. The workspace workflow binds a CI-qualified PR head to an identical compiled backend/workspace tree at the immutable main source. Record digests, source, run and attempt. Build does not deploy.

Before database changes capture live component identities, compare-and-swap approval, a fresh production backup and successful disposable restore including every private file. Apply **only** `Migration20261021120000` with `scripts/team-migration.cjs` inside the qualified backend image. Use `WOODRIGHT_DESK_SCHEMA_RELEASE=desk-team-v1-20261021` and the exact production identity/source gates already required by the desk runner. Do not run generic production `db:migrate`, seed or MANGO migrations. Verify all unrelated migration ledger rows remain unchanged. The two additive tables are `woodright_company` and `woodright_desk_record`.

Promote the new qualified backend/storefront pair through the existing release controller, global and environment leases and exact owner approval. Preserve the current private file volume and feature flags. Companies, record assignments, audit and operation receipts commit atomically. Existing customers, orders, prices and catalogue records are not migrated or rewritten.

Install the entire qualified governance bundle. Pull the exact workspace digest before deployment. Create a protected, checksum-bound owner intent from the user's authorization with `owner_decision=approved`, `scope=team_workspace`, exact `source_sha`, `image`, and `url=https://woodright.ru/os`. This is a separate workspace release, not a rewrite of commerce ACTIVE_RELEASE.

`deploy-team-workspace.py` defaults to a read-only plan. Its deploy mode takes the global lease and a workspace lease, verifies the exact backend/component and workspace baseline, uses only cached digest images, and records rollback material before changes. First deployment requires expected workspace source/ref `absent`. The workspace has no database credentials or private file mount. Its persistent session secret is generated on the VM in a protected file, never printed or committed. Docker owns restart; no parallel systemd/Dokploy controller or automatic Git deployment is installed. Residual Dokploy administrator bypass remains declared as `claim_bypass_closed=false`.

Only `/os` and `/os/…` on the existing HTTPS buyer domain are routed to the new container. The container port is loopback-only; data routes require the signed Secure HttpOnly SameSite session and a real staff actor. Browser requests to mutation routes must match the configured origin. The service's backend revision is pinned; advancing commerce backend requires a qualified explicit workspace update, never automatic adoption.

After deploy verify companies, related contacts/requests/orders, archive/restore, assignments, reminders, company files/history and invite acceptance on disposable data. Public access is login-only. Team invitations use native Medusa one-use, expiring invitations and auth identities; invite tokens stay in URL fragments and request bodies, and native access-log redaction remains in place. No mail is sent by the workspace. Never create production employees or issue invitations to invented recipients. The employee supplies their own password.

Capture five authenticated stable public DOM samples (`at`, `url`, `heading`, `connected=true`, consistent `marker`) and finish with the controller's finalize mode and the checksum-bound evidence file. Only then is workspace ACTIVE_RELEASE marked verified. Run buyer smoke checks and repeat the production backup/restore with private attachments. Before real writes a workspace failure rolls back only its own route/container; after new work preserve data and use forward repair. Never restore an old commerce dump over new employee work.

Existing staff sign in with credentials verified by native Medusa authentication. The owner explicitly chose to retain their existing credentials on 2026-10-21; the workspace does not impose a new-password length rule during login. New invitations and voluntary password changes still require 12 characters. Never enter or choose a new owner password on their behalf. The self-service endpoint verifies the current password against the authenticated user's native identity. Do not store staff passwords in fixtures or release artifacts.

An explicitly authorized update may replace a pending `deployed_not_verified` workspace without falsely finalizing it first. The controller treats PENDING_RELEASE as the latest baseline, checks its exact container identity, source, image and compose/router checksums under both leases, and archives its metadata. A stale pending record cannot fall back to older ACTIVE_RELEASE metadata. Failed updates restore the prior container configuration and release metadata; verification still requires five authenticated public DOM samples.
